Обзор исходников от 1 ноября 2026 года. Позднее проверены systemd и схема
рабочей БД основного сервера: см. `SERVER_LAYOUT.md`. Реальные ограничения
SSH-пользователя обновления, настройки прокси и содержимое записей не проверялись.

Уточнение после следующего запроса владельца: пункты 1 (права) и 11 (health
check обновления) исправлены локально. Пункт 4 (конкурентная запись) оставлен
в плане без реализации; пункт 2 (пароли) отложен по решению владельца.
Добавлен Telegram-архив создания/изменения/удаления: `CalendarBot/ARCHIVE.md`.
Проверка текущего набора: 46 тестов прошли. Продакшен не обновлялся.

## Развёртывание

По информации владельца, основной API работает на `http://roksical.online:8011/`,
а бот — на другой машине. Бот через SSH вызывает обновление основного сервера
отдельным пользователем с ограниченными правами, затем перезапускает себя.
Реализация этой цепочки находится в `CalendarBot/bot.py` (`_run_update_remote`,
`update_decision`) и `scripts/update_prod.sh`. Порт 8001 в локальных значениях
по умолчанию не отражает фактический порт продакшена.

## Устройство

- `CalendarServer/server.py`: FastAPI, маршруты и зависимости авторизации.
- `CalendarServer/database.py`: репозиторий, бизнес-правила, права, история,
  регистрация и выдача изменений.
- `CalendarServer/database_models.py`: SQLAlchemy-модели и SQLite.
- `CalendarService`: Pydantic-модели и DTO, роли, версии протокола,
  HTTP-клиент и кеш десктопа. Это одновременно контракт и часть клиентской логики.
- `CalendarDesktop`: PyQt5, календарь года, редактор, группы, QThread-запросы,
  опрос `/updates` каждые пять секунд.
- `CalendarWeb`: отдельная раздача статики FastAPI; интерфейс на vanilla JS.
- `CalendarBot`: регистрация, согласование доступа, просмотр и редактирование
  событий, управление обновлением.

Исторические `annual` и `daily` сохранены: первое — интервал конкретных дат,
второе — ежегодно повторяющийся день/месяц. Менять эти значения без миграции
протокола и данных не следует.

## Выполненное изменение: Google в фоне

Событие, запись журнала изменений и задание Google теперь сохраняются одной
транзакцией. HTTP-запрос не вызывает Google. Отдельный поток, запускаемый через
lifespan FastAPI, обрабатывает `google_sync_jobs`. Удаление также идёт через очередь.
Первоначальная выгрузка группы использует тот же механизм и возвращает `queued`;
`inserted` и `updated` в этом ответе оставлены равными нулю для старых клиентов.
Обновлённые клиенты показывают число поставленных в очередь событий.

Задачи переживают перезапуск. При ошибке повторяются с задержкой до 300 секунд;
последующие операции того же события ждут, другие события продолжают отправляться.
Внешние запросы выполняются без открытой транзакции SQLite. Новому событию заранее
выделяется Google ID, который повторно используется при повторе вставки после сбоя.
Поэтому `google_event_id` в ответе означает выделенный ID, а не подтверждение
фактического появления события в Google.

Google API transport теперь отдельный на поток, с сетевым таймаутом 30 секунд.
В десктопе POST запускается через слот объекта в рабочем QThread. Тест с задержанным
ответом проверяет, что GUI продолжает обрабатывать таймеры во время запроса.

Для текущего запуска через `python -m CalendarServer.main` используется один
процесс API на БД. Новый обработчик рассчитан на эту схему. Несколько Uvicorn workers
или параллельно запущенных серверов с одной БД потребуют атомарного захвата заданий.

Новая таблица создаётся существующим `Base.metadata.create_all` при старте.
Перед обновлением рабочей установки нужна резервная копия SQLite. Достаточно
обновить сервер и перезапустить его; для исправления потока GUI нужна новая
сборка десктопа. Продакшен и GitHub этим изменением не обновлялись.

## Приоритет 1: права, учётные данные, сохранность данных

1. **Унифицировать проверку прав при обновлении событий.** В
   `EventRepository.update_event` ветка `daily` не проверяет право редактировать
   существующую группу. Ветка `annual` проверяет исходную группу, но не целевую
   при смене `type_id`. Нужна единая проверка обеих групп и API-тесты отказа.
2. **Хранить хеши паролей.** `authenticate_user` хеширует прочитанный из БД пароль
   и сравнивает с вводом, поэтому сама БД содержит исходный пароль. Регистрация
   также записывает открытый пароль. Ввести формат хеша и совместимую миграцию
   старых записей; в клиенте использовать системное хранилище вместо открытых
   паролей в QSettings, в вебе убрать пароль из localStorage.
3. **Проверить HTTPS фактического API.** Сообщённый адрес использует HTTP.
   При прямом подключении к этому адресу логин, пароль и bearer-токен передаются
   без TLS. В репозитории уже есть Caddyfile, но его наличие не подтверждает,
   что текущие клиенты используют HTTPS или что прямой порт закрыт.
4. **Сделать настоящий optimistic locking.** `update_event` принимает клиентскую
   версию и присваивает её без сравнения с текущей. Удаление использует `<=`.
   Ввести атомарную запись по ожидаемой версии, серверное увеличение и HTTP 409;
   показать конфликт в клиентах, чтобы два редактора не затирали изменения.
5. **Миграции и восстановление БД.** `create_all` создаёт отсутствующие таблицы,
   но не обновляет существующие колонки. Единственная старая Alembic-миграция
   не воспроизводит нынешнюю схему с нуля. Нужны актуальная baseline-миграция,
   процедура обновления существующей БД и проверяемое восстановление из backup.

## Приоритет 2: надёжность синхронизации и эксплуатации

6. **Улучшить протокол `/updates`.** Курсор по времени с точностью до секунды
   и чтение через `created_at > since` могут терять изменения на границе секунды.
   Перейти на монотонный ID журнала. Отдельно передавать изменения групп и прав,
   удалять из клиентского кеша события, вышедшие из выбранного года.
7. **Сделать очередь наблюдаемой.** Добавить административный статус: размер,
   возраст первой задачи, последние ошибки, ручной повтор. Сейчас ошибки есть
   в логах и колонках `attempts`, `retry_at`, `last_error`; интерфейс их не показывает.
   Нужны правила для отмены старых задач при выключении синхронизации и изменения
   настроек группы. Повторяющаяся постоянная ошибка сейчас повторяется бессрочно.
8. **Корректно переносить Google-копии.** Смена группы/целевого календаря до сих
   пор не удаляет старую копию. Хранить фактические Google calendar ID и event ID
   для каждой привязки, отдельно моделировать перенос, удаление Google-копии
   вручную и отмену синхронизации. Удалённые Google ID нельзя считать свободными
   для повторной вставки без учёта tombstone/409.
9. **HTTP-клиент десктопа.** В `CalendarService/service.py` запросы без таймаутов,
   обработка HTTP-ошибок неполная. Повтор GET после 401 передаёт аргументы не как
   `params`. Нужны явные таймауты, единый разбор ошибок и безопасный повтор
   авторизации без автоматического дублирования неидемпотентных POST.
10. **Завершить обработку ошибок загрузки в GUI.** Теперь исключение фонового POST
    возвращается как ошибка и освобождает `in_flight`, но нет полноценного
    состояния «не сохранено», сообщения и осознанного повтора. Редактор очищает
    dirty-флаг раньше подтверждения сервера; повторные изменения того же объекта
    во время отправки требуют неизменяемого снимка и сопоставления ответа версии.
11. **Проверять результат обновления.** `update_prod.sh` после всех неудачных
    health checks всё равно печатает `UPDATE_DONE` и завершает работу успешно.
    Возвращать ненулевой код, проверять ожидаемую сборку и фактический порт 8011,
    предусмотреть rollback. Бот должен обновлять себя только после подтверждения
    работоспособности API. Сам сценарий сейчас перезапускает бота, но явно не
    делает `git pull` на его машине: проверить, обеспечивает ли это локальный
    сервис/обёртка. Ограничение SSH forced command проверять на реальном сервере.

    Выполнено: `scripts/check_health.py` читает порты из `.env` и окружения,
    проверяет статус API и совпадение протокола/сборки API и веба с локальными
    исходниками. После 15 неудачных попыток возвращает код 1. Благодаря `set -e`
    скрипт обновления тогда не пишет `UPDATE_DONE`, а бот не перезапускается
    по ветке успеха. Rollback и обновление исходников самого бота остаются
    отдельными задачами. Проверка build различает сборки только при корректном
    обновлении `BUILD` в процессе релиза.

## Приоритет 3: контракт, тесты, сопровождение

12. **Общий источник ролей.** В `CalendarWeb/static/app.js` нет `manager`, а ранг
    `owner` отличается от Python. Генерировать клиентское описание из контракта
    или передавать capability-флаги сервером. Проверить соответствие интерфейса
    серверным правам: например, `member` описан как редактирующий события,
    а кнопки редактора требуют `EDITOR`.
13. **Валидировать DTO по виду события.** Проверять обязательные даты для `annual`,
    порядок интервала, допустимые день/месяц для `daily`, включая 29 февраля.
    Текущий Google-маппинг строит повторение через текущий год и падает для
    29 февраля в невисокосном году.
14. **Разделить серверный репозиторий и общий пакет.** Вынести пользователей,
    права, события и интеграции из большого `database.py`; HTTP-клиент и кеш
    десктопа отделить от чистых DTO. Убрать отладочные `print`, унифицировать
    типы возвращаемых значений и имена (`db_cashe`, разные EventRepository).
15. **Согласовать зависимости и CI.** Полный `requirements.txt` не содержит
    `paramiko`, хотя серверный содержит. Выделить extras desktop/server/bot/dev,
    фиксировать воспроизводимые версии. CI сейчас собирает релизный exe по тегу;
    добавить pytest на push/PR, API-тесты с отдельной БД и проверки прав.
16. **Актуализировать документацию.** README веба и бота называют рабочие модули
    заготовками. Нужен корневой README с реальной схемой двух машин, портами,
    окружением, регистрацией первого администратора и выпуском клиента.

## Проверка выполненных изменений

`python -m pytest -q -p no:cacheprovider`: 30 тестов прошли на локальной Windows.
Проверены транзакционность outbox, восстановление обработчика, порядок
создания/изменения/удаления, повтор и независимость разных событий, выключенная
синхронизация, постановка группы в очередь и отзывчивость GUI при задержке API.
Реальный Google OAuth/API и продакшен не использовались. Отдельный следующий
приёмочный шаг — сохранить, изменить и удалить тестовое событие в синхронизируемой
группе после обновления сервера и проверить его состояние в Google.
