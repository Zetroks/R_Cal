# Архив событий в Telegram

Бот может отправлять в отдельную группу JSON-документ при создании, изменении
и удалении события из любого клиента. В нём полный снимок события, настройки
его группы, действие, автор, UTC-время, номер записи `sequence` и уникальный
`archive_id`. Пароли пользователей и токены туда не попадают.

## Подключение

1. Обновить и перезапустить API на основном сервере, затем обновить бота на
   второй машине. При старте API создаст новую таблицу `event_archive` существующим
   механизмом `create_all`. Перед обновлением сделать копию SQLite.
2. Создать закрытую группу, добавить бота и разрешить ему отправку документов.
3. От имени администратора (`TELEGRAM_ADMIN_ID`) отправить в этой группе
   `/archive_chat` (при необходимости `/archive_chat@имя_бота`). Бот покажет ID.
4. В `.env` **на машине бота** указать `TELEGRAM_ARCHIVE_CHAT_ID=-100...`
   с полученным ID и перезапустить сервис бота. На API эту переменную задавать
   не нужно. `CAL_BOT_SECRET` на обеих машинах должен совпадать; для архивных
   маршрутов используется существующая проверка администратора бота.
5. Отправить `/archive_snapshot`. Все существующие события в обоих форматах
   попадут в архив. Последующие изменения отправляются автоматически.

Команды настройки доступны только администратору бота. Группа должна оставаться
закрытой: архив содержит полные данные всех событий без маскирования restricted.

## Доставка и восстановление

Сохранение события не обращается к Telegram. Снимок записывается в одной
транзакции с событием, бот опрашивает API каждые 10 секунд, забирая до 10 записей.
После успешной отправки каждого документа бот подтверждает запись API. Если
Telegram или сеть недоступны, неподтверждённые записи остаются для повторения.
При незаданном ID группы журнал на сервере всё равно накапливается.

Сбой после отправки и до подтверждения может дать повторный файл. Для
восстановления экспортировать Telegram-чат **вместе с документами**, разобрать
JSON, убрать дубликаты по `archive_id`, упорядочить по `sequence`. Ключ события —
`(kind, event.id)`. `create`, `update` и `snapshot` заменяют снимок по ключу;
`delete` удаляет. Повторный `/archive_snapshot` добавляет снимки текущих событий,
не сбрасывая журнал. Файл изначального снимка содержит то же представление,
что и последующие изменения. Номера определяют порядок в пределах одной БД;
при восстановлении сервера со старой копии БД нужно отдельно учитывать новую
линию истории и возможное повторное использование числовых ID.

Готовый автоматический импортёр в SQLite пока не добавлен. Это архив событий,
а не копия всей БД: пользователи, пароли и назначения прав не архивируются.
При потере сервера до доставки последних записей эти записи будут потеряны;
обычный резервный backup SQLite всё равно полезен. Доставленные записи пока
сохраняются и в `event_archive`, автоматической очистки нет.

Эта реализация рассчитана на один процесс бота: параллельные экземпляры могут
присылать дубликаты, но идентификаторы позволяют их отфильтровать.
